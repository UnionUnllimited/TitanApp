# titan-icmp-gw — аварийный транспорт поверх ICMP

Демон для ноды. Нужен, когда IP ноды **отвечает на ICMP (ping проходит), но TCP и
UDP до неё заблокированы**. Демон принимает датаграммы туннеля, завёрнутые в ICMP
Echo, разворачивает их и отдаёт по UDP во **внутренний inbound** ноды (тот, что уже
работает). Ответы уходят назад как ICMP Echo Reply.

Это аварийный режим, не замена основного транспорта. На чистом канале с хостинга
владелец намерял по нему ~64 Мбит/с.

## Как это устроено

```
iPhone (клиент в libXray)                        Нода
┌───────────────────────────┐                   ┌─────────────────────────────┐
│ ядро Xray (UDP-протокол:   │                   │ titan-icmp-gw               │
│  WireGuard / Hysteria2 /   │                   │                             │
│  VLESS·VMess over mKCP)    │                   │  raw ICMP socket            │
│        │ UDP               │   ICMP Echo        │     │                       │
│        ▼                   │   Request          │     ▼ UDP на 127.0.0.1      │
│ 127.0.0.1:LOCAL (ICMP-шим) │ ───────────────▶  │  внутренний inbound ноды     │
│        ▲                   │   Echo Reply       │     ▲                       │
└────────┼───────────────────┘  ◀─────────────── └─────┼───────────────────────┘
         └── приходят только как ответы на запросы ────┘
```

Шим — это **тупая труба датаграмм**. Поверх ICMP нет ни надёжности, ни переупорядочивания:
потери чинит внутренний протокол (у него свой контроль). Заголовок перед каждой
датаграммой — 8 байт:

| смещение | размер | поле    | описание                                        |
|----------|--------|---------|-------------------------------------------------|
| 0        | 4      | magic   | `0x54544E31` («TTN1»), big-endian               |
| 4        | 2      | session | номер сессии, выбирает клиент, big-endian        |
| 6        | 2      | seq     | счётчик датаграмм в своём направлении, big-endian |
| 8        | …      | inner   | внутренняя датаграмма (payload ядра), как есть    |

`session` несёт идентификатор клиента **в заголовке**, а не в поле ICMP id: на iOS
клиент использует непривилегированный datagram-сокет ICMP, где id принадлежит ядру ОС,
и оператор по пути может его переписать (NAT). Поэтому демон в ответе **повторяет тот же
ICMP id и ICMP sequence**, что были в запросе, — иначе ядро клиента не отдаст ответ в его
сокет.

### Слоты ответов (почему клиент «поллит»)

Нисходящий трафик по ICMP существует только как **ответы на запросы**. Поэтому клиент
держит несколько запросов «в полёте» (поллы), а демон считает каждый пришедший запрос
одним **кредитом** — слотом, в который можно положить одну нисходящую датаграмму (как в
hans / ptunnel). Если данных для клиента пока нет, слот держится до `-slot-ttl`, затем
уходит пустой ответ (это и keepalive, и освобождение слота для учёта на клиенте).
Очереди ограничены; при переполнении теряется самая старая датаграмма — внутренний
протокол это переживёт, а демон не должен вставать.

### Обычный ping продолжает работать

Пока демон держит raw-сокет, ядро ноды **нельзя** оставлять отвечающим на echo, иначе на
один ping придут два ответа. Демон сам ставит `net.ipv4.icmp_echo_ignore_all=1` (флаг
`-manage-icmp-ignore`, по умолчанию включён) и **сам отвечает на обычные ping** (без
нашего magic) — зеркалит их тело обратно. Мониторинг доступности ноды по ping работает
как раньше. При остановке демон возвращает sysctl в прежнее значение.

## Какие серверы идут через этот транспорт

Серверной настройки маркера не требуется. На стороне клиента (как уже сделано для
маркеров `tfo` / `pktup`) через шим идёт сервер, у которого **в имени или в поле `titan`
его proxy-outbound есть подстрока `icmp`** (регистронезависимо) **и** сам outbound —
UDP-протокол (WireGuard, Hysteria2 или VLESS/VMess over mKCP). Всё остальное идёт
по-старому, байт в байт. Внутренний inbound (`-inner`) на ноде должен соответствовать
этому UDP-протоколу.

## Запуск

Нужны права на raw ICMP сокет (`CAP_NET_RAW`) и на запись sysctl (`CAP_NET_ADMIN`) —
либо запуск от root.

### Docker Compose

1. В `docker-compose.yml` подставьте `<INNER_PORT>` — UDP-порт внутреннего inbound ноды.
2. Соберите и запустите:

   ```sh
   docker compose up -d --build
   docker compose logs -f
   ```

Контейнер работает в сети хоста (`network_mode: host`), чтобы принимать ICMP на публичный
IP ноды и отвечать с него. `<NODE_IP>` нигде прописывать не нужно: демон слушает все
интерфейсы и форвардит на `127.0.0.1`.

### Отдельным бинарником (без Docker)

```sh
/usr/local/go/bin/go build -trimpath -o titan-icmp-gw .
sudo setcap cap_net_raw,cap_net_admin+ep ./titan-icmp-gw
./titan-icmp-gw -inner 127.0.0.1:<INNER_PORT>
```

Если `CAP_NET_ADMIN` выдать нельзя, выставьте sysctl руками и выключите управление им:

```sh
sudo sysctl -w net.ipv4.icmp_echo_ignore_all=1   # демон сам ответит на обычные ping
./titan-icmp-gw -inner 127.0.0.1:<INNER_PORT> -manage-icmp-ignore=false
```

(как альтернатива sysctl — правило nftables, которое гасит ядерный авто-ответ на echo.)

### Файрвол

ICMP Echo (type 8) до `<NODE_IP>` должен доходить до хоста, а Echo Reply (type 0) —
уходить. Если на ноде есть правила, режущие ICMP, — разрешите эти два типа.

## Флаги

| Флаг                    | По умолчанию        | Назначение                                                     |
|-------------------------|---------------------|----------------------------------------------------------------|
| `-inner`                | `127.0.0.1:51820`   | адрес внутреннего inbound (UDP), куда форвардить                |
| `-listen`               | `0.0.0.0`           | локальный IPv4 для raw ICMP сокета                              |
| `-slot-ttl`             | `250ms`             | сколько держать неизрасходованный слот до пустого ответа        |
| `-idle-timeout`         | `120s`              | закрыть сессию после стольких без трафика в обе стороны          |
| `-max-datagram`         | `1500`              | максимальный размер внутренней датаграммы (буфер чтения)         |
| `-slot-queue`           | `64`                | максимум невыполненных слотов на сессию                         |
| `-down-queue`           | `256`               | максимум буферизуемых нисходящих датаграмм на сессию            |
| `-manage-icmp-ignore`   | `true`              | ставить `net.ipv4.icmp_echo_ignore_all=1` на время работы       |

Параметры клиента (под MTU ~1200–1280 и keepalive каждые ~15–20 с) задаются на стороне
приложения; демон под них подстраивается сам.

## Логи и приватность

По умолчанию в лог идут только строки открытия/закрытия сессии с её номером. IP клиентов
и адреса в лог не пишутся. Для отладки: `TITAN_DEBUG=1` — тогда в лог попадают адрес
внутреннего inbound и ошибки отдельных датаграмм.

## Тесты

```sh
go test ./...                       # формат (golden-векторы), логика сессий/слотов/ответов
go test -race ./...                 # то же под детектором гонок
go test -tags e2e -run TestE2E -v   # сквозной тест по loopback (нужен root; см. ниже)
```

Сквозной тест `TestE2ELoopback` поднимает демон на `127.0.0.1` с UDP-эхо как внутренним
inbound и сам выступает клиентом (datagram-сокет ICMP, как на iOS): проверяет полный
путь запрос → форвард во внутренний inbound → ответ с зеркальным ICMP id. Требует root и
возможности выставить `icmp_echo_ignore_all`; в CI и обычном `go test` не участвует
(собран под тегом `e2e`).

## Ограничения

- Сессия ключуется по `session` из заголовка. Если два клиента случайно выберут один и
  тот же `session` (u16), их потоки пересекутся. Клиент выбирает `session` случайно;
  коллизия маловероятна.
- Это не `udp2raw`. Стоковый `udp2raw` на ноде несовместим с нашим форматом (у него своё
  рукопожатие, AES/HMAC и anti-replay). Здесь свой формат и свой демон.
- Транспорт аварийный: без шифрования на уровне шима (его даёт внутренний протокол) и без
  своей борьбы с потерями.
