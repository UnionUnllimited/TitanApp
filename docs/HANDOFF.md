# Titan VPS: передача проекта

Обзор репозитория для разработчика, который продолжит работу. Ветка с последними
изменениями: `claude/exciting-ptolemy-oiy9r6`.

## Безопасность

Репозиторий публичный. В код, коммиты и issues не должны попадать домен и IP
админки и бота, адрес и токен панели, ключи подписки, UUID, ключи шифрования.
Секреты сборок (подпись iOS, App Store Connect) лежат в GitHub Secrets.

## Сборки

Каждый пуш в `claude/**` или `main` с изменениями в нужной папке запускает CI.
Релизы для обновлялок Android и Windows выкладываются только из ветки по умолчанию и `main`: пуш в
любую другую ветку (`claude/ios-int` и т. п.) только собирает, иначе он выкатил бы пользователям
старую версию другой платформы (так вышли `android-283/284` и `windows-86`). Тестовые APK — пуш в
`android-dev/**` (pre-release `android-test-N`, обновлялка его не предлагает).
Результат выкладывается в GitHub Releases:

- Android: тег `android-N`, файлы `titan-vps-arm64.apk`, `titan-vps-armv7.apk`, `titan-vps-universal.apk`
- Windows: тег `windows-N`, файлы `titan-vps-setup.exe`, `titan-vps.msi`. `xray.exe` собирается в CI из Xray-core v26.9.30 с патчем `scripts/ios-patches/xray-tfo` и тегом `tfogo_checklinkname0`
- iOS: тег `ios-N`, файл `TitanVPS-unsigned.ipa` (без подписи, для сервисов подписи и Sideloadly)
- iOS в TestFlight: workflow `testflight.yml`, запускается вручную (Actions → TestFlight → Run workflow)
  или созданием ветки `testflight/*` либо тега `testflight-*` (версия 1.0.0).
  App Store Connect принимает только сборки с iOS 26 SDK, поэтому обе iOS-сборки выбирают на раннере Xcode 26+;
  `UIDesignRequiresCompatibility` оставляет на iOS 26 прежний вид (без Liquid Glass).
  Подпись автоматическая через ключ App Store Connect API; нужные секреты перечислены в начале файла.
  Bundle ID: `com.titanvps.ios` (туннель `com.titanvps.ios.tunnel`, виджеты `com.titanvps.ios.widgets`);
  прежний `su.titanvps.app` остался за сервисом подписи. Манифесты приватности: `PrivacyInfo.xcprivacy`
  в `ios/TitanVPS`, `ios/TitanTunnel` и `ios/TitanWidgets`.

Ядро iOS долго собирается без кэша: кэш сбрасывается при изменении `scripts/ios-patches/**`.

## Где что в коде

- Разбор подписки и правка конфигов на iOS: `ios/TitanVPS/Subscription.swift`
  (`dropTfo` снимает TFO панели на обычных серверах, `applyTfo` включает TFO по имени сервера или полю `titan`;
  `fitXhttpInSyn` правит XHTTP для TFO-серверов).
- То же на Android: `app/src/main/java/com/titanvps/app/core/XrayConfigs.kt`; на Windows: `desktop/src/main/kotlin/com/titanvps/desktop/XrayConfigs.kt`.
- Пинг: iOS `ios/TitanVPS/XrayPing.swift`; Android `app/.../core/PingService.kt`; Windows `desktop/.../Repository.kt` (`PingEngine`).
  Он меряет новое соединение через сервер (рукопожатие прокси, DNS, TLS сайта), это не задержка: на iOS
  в «Проверить соединение» и в Live Activity — тёплая задержка (`ConnectionCheck.swift`, ниже).
  На iOS ответивший сервер меряется второй раз в том же вызове pingBatch, на том же экземпляре Xray
  (`warmTimeout`, патч libXray `xray-tfo/apply_libxray.py`), как вторая попытка Android на тёплом ядре: соединения
  новые (TCP и TFO заново), но состояние выхода тёплое, как в работающем туннеле (билет 0-RTT VLESS-encryption,
  XMUX); показывается лучшая из двух. То есть число — тёплое новое соединение, а не самое первое после смены
  сервера. Раньше вторая попытка шла отдельным вызовом с новым экземпляром: тёплыми были только cookie TFO ядра
  и DNS. Ответ медленнее 1500 мс при пинге списка показывается сразу (бледно, со спиннером) и меряется ещё раз
  после списка, вместе с повтором ошибок, затем показывается лучший из двух (как `RECHECK_ABOVE_MS` на Android).
  Перемер — одна попытка, без второй пробы, по 2 за раз, 6 с, как на Android; но перемеряются не больше 6 таких
  серверов, первые по порядку списка (вкладка на экране первой), остальным остаётся первый ответ: VPN на время
  пинга выключен (на Android он работает), и перемер удлиняет паузу самое большее примерно на 18 с (вдвое — если
  медленные серверы за одним входом, они идут по одному). «Стоп» или уход из приложения во время перемера
  оставляют первый ответ. Пинг одного сервера — без перемера.
- VPN: iOS `ios/TitanVPS/VPNController.swift` и `ios/TitanTunnel/PacketTunnelProvider.swift`;
  Android `app/.../vpn/TitanVpnService.kt`; Windows `desktop/.../AppState.kt`, `Tun.kt`.
  - На iOS профиль VPN хранит конфиг сервера, с которым туннель стартует из Настроек iOS и по «Не отключать VPN».
    После обновления подписки при выключенном VPN приложение пересобирает его, если сервер в подписке
    изменился или пропал (`VPNController.refreshProfile`; по ключу `source` — хешу конфига сервера из подписки
    и версии сборщика `XrayRunConfig.version`, её поднимают при каждом изменении того, что собирают `build` и
    `parseServers`). При «Не отключать VPN» профиль с другим `source` пересобирается и при включённом VPN
    (`setKeepAlive`): когда приложение видит «Подключено» и после каждого обновления подписки (`AppStore.load`).
    Работающий туннель остаётся со своим конфигом, новый — со следующего запуска (в том числе после того, как iOS
    убила туннель). Только из серверов, разобранных этой сборкой: подписка, сохранённая старой
    (`Subscription.parsedBy`), до своего обновления не используется — иначе профиль получил бы её старый конфиг
    с новой версией. Без «Не отключать VPN» профиль работающего туннеля не трогается (если iOS перезапустит туннель
    при сохранении, без on-demand вернуть его некому): новый конфиг — со следующего подключения из приложения или
    обновления подписки при выключенном VPN.
  - Если VPN включился не из приложения, выбранным в приложении становится сервер профиля (`AppStore.followTunnel`).
  - «Не отключать VPN» (Настройки → Подключение, ключ `keepAlive`, по умолчанию включён) — это VPN On Demand
    (`NEOnDemandRuleConnect`, любой интерфейс). Любое включение (ползунок, смена сервера, возврат после пинга,
    Пункт управления, Siri, Live Activity) сохраняет профиль с `isOnDemandEnabled = keepAlive`. Ручное выключение
    (ползунок, Пункт управления, Siri, ⏻) сначала выключает on-demand, поэтому VPN остаётся выключенным. Пинг и смена
    сервера держат on-demand выключенным, пока туннель перезапускается; `setKeepAlive`, начатый до этого (пересборка
    профиля после обновления подписки), его не включает обратно — как и после выключения переключателя или начала
    подключения за время сборки. «Не отключать VPN», переключённый во время подключения,
    применяется, как только `connect` сохранил профиль. Если VPN включили не из приложения (Настройки iOS, профиль
    до обновления), при подключении приложение приводит on-demand профиля к переключателю. «Автоподключение» теперь
    только включает VPN при открытии приложения: при запуске и при возврате из фона (`RootView.autoconnectOnOpen`).
  - Для обхода (без технического режима) правила on-demand другие: `Connect` только на мобильной сети и `Ignore` на
    остальных (`TunnelSwitch.onDemandRules`). iOS не поднимет обход на Wi‑Fi, а уже работающий туннель `Ignore` не
    рвёт. Переключение технического режима сразу пересохраняет правила профиля.
  - Если наш собственный запуск упал, не дойдя до «Подключено» (туннель не принял конфиг и т. п.), on-demand
    выключается (`VPNController.startFailed`, `TunnelSwitch.waitUntilUp`), иначе iOS перезапускала бы его по кругу.
    Падение после «Подключено» on-demand не трогает — VPN поднимет iOS.
  - Ручное выключение во время паузы пинга (Siri, ⏻, «Выйти») отменяет возврат VPN после пинга
    (`VPNController.offsByHand`, `AppStore.endPing`); «Выйти» останавливает пинг.
  - Подключение, смена сервера и пауза пинга до возврата VPN идут с фоновым временем (`BackgroundTime`,
    `beginBackgroundTask`): иначе iOS приостановит ушедшее приложение, и VPN останется выключенным с выключенным
    on-demand до следующего открытия. Если уйти из приложения во время пинга или проверки TCP (технический режим),
    они останавливаются, и VPN сразу включается снова (пауза, которая ещё идёт, сначала заканчивается).
  - При смене сети туннель через 1,5 с перезапускает Xray и клиент протокола, всё это время с `reasserting`
    («Подключаемся…»). При ошибке повторяет через 1, 2, 4, 8, 15, 30 с; без сети ждёт сеть. Туннель завершается
    только после ~минуты неудач, и его поднимает on-demand. Запуск, остановка и перезапуски идут на одной очереди:
    перезапуск не запустит Xray после остановки туннеля.
  - Сменой сети считается (`PacketTunnelProvider.networkChanged`): первая сеть, если туннель стартовал без неё
    (после перезагрузки); другой интерфейс (Wi‑Fi ↔ LTE); пауза без сети от 15 с; пропал адрес интерфейса
    (`getifaddrs`, кроме link-local; новый адрес рядом со старыми, например временный IPv6, — не смена). Та же сеть
    после короткой паузы (тоннель, мёртвая зона в дороге) с теми же адресами — не смена: раньше пустой путь на время
    паузы читался как «нет сети → LTE», и перезапуск через 1,5 с рвал все соединения (YouTube) и результаты
    observatory. Перезапуски при смене сети — не чаще раза в 20 с: следующий в этом окне откладывается до его конца,
    а не отбрасывается; отложенный не делается, если Xray к тому времени снова на сети, на которой запущен, с теми же
    адресами, а сети, через которые он ходил в ожидании, ещё есть в пути (Wi‑Fi → LTE → Wi‑Fi: LTE остаётся). LTE →
    Wi‑Fi → LTE, когда Wi‑Fi ушёл, — перезапуск в конце окна: соединения, открытые через Wi‑Fi, висели бы. Если Xray
    лежит после неудачного перезапуска — без ожидания. Паузу и окно считают монотонные часы (`CLOCK_MONOTONIC`: их не
    сдвигает смена времени на телефоне, во сне идут), окно — не дольше 20 с. Каждый пишет в журнал туннеля
    «перезапуск при смене сети: <было> → <стало>[, адрес сменился][, пауза N с]» (Технический режим →
    «Память туннеля»).
  - Xray каждый раз получает копию (`dup`) fd utun: Go закрывает свой fd, когда старый экземпляр собирается
    сборщиком мусора. Раньше из-за этого VPN падал вскоре после переключения Wi‑Fi ↔ LTE.
- Интерфейс iOS: общие кнопки, переключатели, строки настроек, тосты и хаптика — `ios/TitanVPS/Components.swift`;
  ползунок «Выкл | Вкл» (перетаскивание, блокировка на время пинга) — `PowerSlider.swift`;
  «Проверить соединение» (запросы через работающий VPN: задержка, страна и IP выхода) — `ConnectionCheck.swift`.
  Задержка тёплая: одно соединение через VPN к `www.gstatic.com/generate_204` по HTTP (Network.framework),
  первый запрос его прогревает (рукопожатие прокси — REALITY, mlkem, XHTTP, — DNS, маршрут) и не считается,
  следующие три идут по тому же соединению, показывается медиана: телефон → VPN-сервер → Google и обратно.
  Первый запрос нового соединения на рабочем VPN часто длится больше секунды — его раньше и показывали
  («1 575 мс» красным в Dynamic Island). Google, а не российский сайт: российские домены панель пускает мимо
  VPN. Числом задержка показывается, только если она меньше 300 мс (`Latency` в `ios/Shared/VPNActivity.swift`):
  до 120 мс зелёная, дальше обычным цветом, красной и оранжевой не бывает; от 300 мс — «Работает · медленно»
  (VoiceOver: «Соединение работает, медленно»), Google не ответил, а Cloudflare ответил — «Работает» без числа;
  неудачи — как раньше. Запрос на прогретом соединении — несколько сотен байт;
  вкладки Главной «Страны» (Wi‑Fi / LTE) и «Обходы» (только LTE) — `HomeView.tabChip`: на телефоне сети второй
  строкой, в широком окне в одну строку, если помещается; когда рядом с ними не помещается обычный «Пинг» (крупный
  текст на 375 pt), он узкий: значок над словом, как в макете.
- «Личный кабинет» на iOS (`CabinetView.swift`): вкладка «Подписка» (дни, трафик, устройства, «Ваш ID») с кнопкой
  «Продлить подписку» — она открывает «Тарифы», App Store первым, — и вкладка «Тарифы» сайта: тарифы, способы и
  «Есть код?». Страница тарифа открывается внутри приложения (`PaymentView.swift`, заголовок «Тариф»), кнопки по
  дороге к ней нейтральные («Продолжить · СБП»). Вкладка «Тарифы» показывается там же, где «Другие методы»
  (`AppStorePurchases.otherMethods`, ниже).
- Требования App Review (iOS):
  - «Конфиденциальность» при первом запуске, после заставки и до ввода ключа (`PrivacyNoticeView` в `RootView.swift`,
    ключ `privacyAccepted`): что приложение делает с данными и трафиком, согласие на VPN-конфигурацию, ссылка на
    `docs/PRIVACY.md`. Пока не принято, ссылки `titanvps://` ждут, подписка не обновляется, «Автоподключение»
    не срабатывает.
  - «Тарифы» (`PaywallView.swift`) открываются со строки «Подписка истекла · Продлить» на Главной, кнопкой
    «Продлить подписку» на вкладке «Подписка» и в кабинете, кнопками «Добавить ГБ» и с экрана ввода ключа
    («Нет ключа?» → «Подписка через App Store»). Сначала App Store (StoreKit 2, `Purchases.swift`: `ProductIDs` —
    заглушки до App Store Connect, `AppStorePurchases`): подписки с описанием из App Store Connect, для «Добавить ГБ»
    ещё пакеты ГБ (расходуемые), «Оплатить через Apple», «Восстановить покупки», «Управление подпиской», с ключом —
    «Ввести код предложения» (коды предложений App Store; коды сайта — во вкладке «Тарифы» кабинета), условия
    автопродления; ссылки на EULA Apple и политику всегда. Нет подписок — «Тарифы App Store скоро появятся», не
    загрузились — «Не удалось загрузить тарифы App Store» и «Повторить»; нет пакетов ГБ — их карточки нет вовсе.
    Пакеты ГБ нужно завести в App Store Connect до ревью: гигабайты, которые продаёт бот и расходует приложение,
    должны продаваться и через App Store (3.1.3(b)). Ниже «Другие методы» без цены (кабинет сайта во внешнем
    браузере; без ссылки на сайт — бот). Тап по напоминанию о трафике сначала закрывает листы вкладок (кабинет,
    устройства, «О приложении»: UIKit показывает один лист за раз), потом открывает «Тарифы». Транзакция
    завершается только после того, как бот её принял (`AppStorePurchases.deliver` → `Config.purchaseEndpoint`, пока
    `nil`); до этого StoreKit отдаёт её снова при каждом запуске (`Transaction.updates`). Без ключа покупка идёт с
    токеном этого устройства, бот возвращает ключ, и приложение входит с ним; «Восстановить покупки» на экране
    ввода ключа так же возвращает ключ подписки, купленной на другом устройстве. Протокол —
    `docs/BACKEND-APPSTORE.md`; пока endpoint нет, в заметках для App Review нужен демо-ключ.
  - **Решение владельца: «Другие методы» и вкладка «Тарифы» кабинета — во всех витринах**
    (`AppStorePurchases.otherMethodsEverywhere = true`). App Review разрешает кнопки и ссылки на оплату мимо App
    Store только в витрине США (3.1.1(a), 3.1.3), а оплату цифровых услуг внутри приложения мимо App Store — нигде
    (3.1.1), так что с ними ревью могут отклонить. `false` оставит их только в витрине США (`Storefront.countryCode` =
    `USA`); с ключом «Другие методы» тогда всё равно появятся, если App Store не отдал ни одной подписки
    (`noSubscriptions`), чтобы истёкшему ключу было что нажать. Остальные пути к боту и сайту — тот же переключатель
    (`AppStorePurchases.linksOut`): «Где взять ключ» с ботом на экране ввода ключа, «Открыть сайт» на вкладке

## Заголовки подписки

Что приложение читает из заголовков ответа сервера подписки (в Remnawave — Настройки подписки → Дополнительные
заголовки ответа; имена без учёта регистра). Provider ID, как у Happ, не нужен: подписку приложение берёт только
со своих хостов.

- `subscription-userinfo` (`upload`, `download`, `total`, `expire`) — трафик обходов и срок подписки.
- `support-url` — поддержка (без него — бот); `profile-web-page-url` — сайт.
- `announce` (можно `base64:…`) — причина, когда в ответе нет серверов.
- `profile-title` — только Android; `profile-update-interval` (часы, 1–168, без него 12) — Android и Windows (на Windows
  подписка обновляется в фоне раз в полчаса, когда старше интервала; при открытии окна из трея — когда старше 30 мин).
- `sniffing-enable` (iOS, Android и Windows; на iOS `SubscriptionAPI.parseInfo` → `SubscriptionInfo.sniffing`, сохраняется с подпиской и
  действует после перезапуска и без сети; на Windows `SubscriptionHeaders.parse` → `SubscriptionInfo.sniffing`, хранится в
  `state.json`, действует со следующего подключения на оба локальных инбаунда, `XrayConfigs.buildProxyConfig`). `1` / `true` / `on` (в любом регистре), другое значение или нет
  заголовка — как всегда: сниффинг TUN-инбаунда из шаблона панели с `enabled: true` (без него `http`, `tls`,
  `quic`, `routeOnly: false`), без заголовка конфиг тот же. `0` / `false` / `off` — `sniffing: {"enabled": false}`, остальное не меняется.
  Без сниффинга у соединения из TUN только IP: доменные правила маршрутизации (панели и наш блок QUIC YouTube) его
  не находят, работают правила по IP (`IPIfNonMatch` резолвит имя ради IP-правил, IP в имя не превращает); домены
  в настройках DNS по-прежнему выбирают, кто резолвит имя; FakeDNS без сниффинга не работает. Действует со
  следующего подключения: `parseServers` помечает конфиг сервера (`_titanSniffingOff`), поэтому смена заголовка
  меняет `source`, и профиль VPN пересобирается, как при других изменениях конфига (`refreshProfile`,
  `setKeepAlive`), — on-demand стартует уже с новым. Технический режим → «Устройство» → «Сниффинг»:
  «включён / выключен (заголовок подписки)» или «включён (по умолчанию)».

## TCP Fast Open на iOS

- Транспорт туннеля — Xray-core (Go, BSD-сокеты). Опции Network.framework
  (`NWProtocolTCP.Options.enableFastOpen`, `NWParameters.allowFastOpen`) действуют только
  на `NWConnection` и к сокетам Xray не относятся. Поэтому TFO включён в самом Xray-core
  (`scripts/ios-patches/xray-tfo`): дайлер tfo-go открывает соединение на первой записи
  через `connectx()` с `CONNECT_DATA_IDEMPOTENT` (то же делает Network.framework) и ставит
  `TCP_FASTOPEN_FORCE_ENABLE`.
- Что выяснено по исходникам XNU (`bsd/netinet/tcp_output.c`, `tcp_timer.c`, `tcp_cache.c`):
  - в SYN идёт не больше `t_maxopd − 40` байт, а до SYN-ACK `t_maxopd` — MSS по умолчанию:
    472 Б для IPv4, 984 Б для IPv6. Если в очереди больше, данных в SYN нет вовсе. Поэтому
    первая запись режется (`tfoSynData4/6`), остальное уходит после рукопожатия;
  - без `TCP_FASTOPEN_FORCE_ENABLE` ядро после двух потерь отключает TFO для всей сети
    (ключ — сигнатура сети, не сервер) на 5 мин, 10, 20… и повторяет потерянный SYN без
    данных. Опция это отключает, tfo-go ставит её на каждый сокет.
- В SYN кладётся только то, что безопасно получить дважды (`tfo_safe.go`): TLS ClientHello,
  заголовки HTTP, тело GET/HEAD/OPTIONS и загрузок XHTTP packet-up (сервер принимает каждую
  один раз по номеру). Прочее (заголовок прокси-протокола с данными) — без TFO.
- На обычных серверах (всё, кроме «Обходов»: «обход» в имени, как `ServerGroup.isBypass`) TFO нет:
  `Subscription.parseServers` снимает `streamSettings.sockopt.tcpFastOpen` (и у `downloadSettings` XHTTP) со
  всех выходов, до `applyTfo` / `applyPacketUp` / `fitXhttpInSyn`, так что метки «tfo» и «pktup» включают его
  снова. Причина — YouTube на АВТО по мобильной сети: DPI оператора отбрасывает данные клиента после
  TFO-рукопожатия (тело XHTTP stream-up, хвост ClientHello сверх ~470 Б SYN), а дайл считается успешным, и
  соединения висят; обычный SYN (как у стокового Xray в других клиентах) проходит. Обходы оставляют TFO
  панели (409380e): под белыми списками он нужен. Android не менялся. `XrayRunConfig.version` поднят до 3.
  Конфиги серверов без TFO появляются с обновлением подписки (сохранённая разобрана старой сборкой,
  `Subscription.parsedBy`); сразу после него профиль VPN пересобирается и при выключенном VPN (`refreshProfile`),
  и при включённом с «Не отключать VPN» (`setKeepAlive`, для следующего запуска: работающий туннель доживает с
  TFO). Без «Не отключать VPN» при включённом — со следующего подключения из приложения (в том числе после пинга).
- Каждое TFO-соединение сверяется с записью ядра (`TCP_CONNECTION_INFO`): ушли ли данные в
  SYN и принял ли их сервер. Это видно:
  - в «Техническом режиме», карточка «TCP Fast Open»: туннель (через `handleAppMessage`) и
    пинг в приложении; «данные в SYN приняты сервером» — TFO действительно сработал;
    «данные ушли, ответа нет» — TFO-соединения после TLS- или HTTP-запроса, закрытые без единого
    полученного байта (так выглядит DPI, отбросивший данные); «SYN отправлен повторно (+1 с)» — TFO-подключения,
    где ядро повторило SYN через 1 с (под `TCP_FASTOPEN_FORCE_ENABLE` само оно это не отмечает), в заметке
    соединения — `SYN sent twice` (`tfo_syn_twice.go`). Признаков два: данные SYN отправлены повторно (счётчик
    повторно отправленных байт ядра; видит повтор SYN с данными и при потере самого SYN, и при потере SYN-ACK,
    с метками времени TCP и без них) или рукопожатие дольше RTT пути на 0,7 с и больше. Время рукопожатия —
    от начала подключения сокета, без поиска имени в DNS и без других адресов, перепробованных до него
    (время всего подключения, `in N ms` в заметке, их включает: рядом в заметке `handshake N ms`). Признак по
    времени видит только потерю самого SYN и только при метках времени TCP: повторный SYN-ACK несёт метку
    первого SYN, а без меток iOS в сотовой сети считает RTT от первого SYN, так что RTT включает повтор; в Wi‑Fi
    без меток RTT нет (0). Ноль на карточке не исключает повтор SYN без данных (запрос cookie), если потерян
    SYN-ACK или на пути нет меток времени. Последние 60 заметок о соединениях там же;
  - в ошибке пинга, в квадратных скобках (`tfo http 438+0 B in 71 ms: data in SYN, acked, handshake 70 ms, rtt 68 ms`).

## Проверка TFO

1. Телефон: «Технический режим» → «TCP Fast Open» → «Обновить» при включённом VPN на
   TFO-сервере (обход с TFO в подписке или сервер с «tfo» в имени). Ждём «TFO работает», растущее «данные в SYN приняты сервером» и нули в
   «не приняты» и «ядро отправило обычный SYN». «cookie ещё не было» — первое соединение
   после смены сети, это нормально.
2. Сервер: в SYN от клиента должны быть `tfo cookie` и `length > 0`, сразу за SYN-ACK —
   ответ сервера, до третьего ACK (значит, данные из SYN приняты):

```
tcpdump -nr /root/t.pcap -vv 'src host <IP клиента> and tcp[tcpflags] & tcp-syn != 0' | paste - - | head
nstat -az TcpExtTCPFastOpenPassive TcpExtTCPFastOpenPassiveFail TcpExtTCPFastOpenCookieReqd
```

## Память туннеля на iOS

iOS даёт туннелю (Packet Tunnel Extension) около 50 МБ `phys_footprint` и при превышении молча
завершает процесс (jetsam). VPN после этого поднимает «Не отключать VPN». Что ограничено и где:

- libXray v26.9.30 сам (`memory/memory_ios.go`, при первом `runXray`): Go `SetGCPercent(10)`,
  `SetMemoryLimit(30 MiB)`, `FreeOSMemory` каждую секунду. GOGC 10 остаётся (GOGC 100 — куча в два раза больше
  живой), `FreeOSMemory` libXray теперь раз в минуту (`xray-mem/apply_libxray.py`, ниже «Батарея на iOS»): выше
  35 МиБ свободные страницы Go раз в 5 с отдаёт сторож, на своих же замерах. «После» в журнале — живая память,
  а не мусор (`restart` отдаёт память сам): перезапуски, освобождавшие 0–3 МБ, держали живой прежний экземпляр
  (ниже). Лимит Go туннель задаёт сам (`titan` `setMemoryLimit`, ниже).
- Патч `scripts/ios-patches/xray-mem` (только iOS, вызывается из `build-libxray-ios.sh` после xray-tfo),
  gVisor-стек TUN в Xray-core: TCP-буферы 32 КиБ на старте и до 128 КиБ (отправка) / 256 КиБ (приём)
  вместо 1 МиБ и 6 / 8 МиБ; окно приёма нового соединения 64 КиБ (`rcvWnd` 0 давал 1 МиБ каждому);
  не больше 1024 TCP-соединений через TUN одновременно (Xray завершает запрос форвардера только
  по закрытии соединения, так что `maxInFlight` считает живые соединения; сверх него новые SYN
  отбрасываются, пока какое-то не закроется); при остановке стека закрываются и его UDP-потоки,
  а не живут до `connIdle`. Не нашлись якоря в новом Xray-core — сборка останавливается с ошибкой
  (нет `stack_gvisor.go` — патч пропускается).
- Тот же патч, транспорты и observatory (`*_mem.go` копируются как `titan_mem.go`, тесты запускает
  `build-libxray-ios.sh`). Какие серверы выбирают балансировщики, их стратегия, стоимости и правила панели не
  меняются:
  - Пулы XHTTP, gRPC и Hysteria — глобальные карты по указателю на stream settings экземпляра: новый
    экземпляр старые записи не находит, и никто их не закрывал. Каждый перезапуск оставлял живой весь набор
    соединений прежнего (XHTTP — до 300 с простоя, gRPC — 30 мин и с ним весь старый `core.Instance`,
    Hysteria с keepAlive 5 с панели — навсегда): 4–8 МБ на поколение, отсюда «40.0 → 40.0», «45.5 → 45.9».
    `internet.TitanCloseTransports` (`titan` `closeTransports`) закрывает всё и очищает карты; туннель зовёт

    (`outbound.Manager.Select`): по 4 в этом порядке leastLoad 20–60 с после каждого старта выбирал из первых по
    алфавиту (самая дешёвая по стоимостям группа панели — в конце), и открытые тогда соединения на них и
    оставались. Перемешанные одним списком — маленькая группа (выходы для YouTube, 8 из 60, у балансировщика
    YouTube в приоритете по стоимости) получала свои первые результаты на секунды позже большой, и до того
    балансировщик выбирал из большой. Поэтому (`titanOrder`): выходы делятся на группы по префиксу
    `subjectSelector` observatory (самому длинному подходящему), каждая перемешивается, группы берутся по
    очереди — в первых 12 есть выходы каждой группы, остальные в случайном порядке. Пробы стартуют строго в
    этом порядке (`titanGate`, очередь по номеру), а не в каком придётся порядке запускаются горутины их
    таймеров; тег, указанный дважды, проверяется один раз. Модель (52 + 8 выходов, 12 слотов, 10% мёртвых держат
    слот 3 с, ответ 0,8 / 1,5 с): пятый результат группы YouTube через 1,1 / 2,1 с (все сразу — 1,0 / 1,8, одним
    перемешанным списком — 3,6 / 6,2). Стенд из 85 выходов (живой сервер: XHTTP REALITY с ML-KEM, gRPC,
    Hysteria, TCP REALITY; ответ проверки через 0,8 с): первые 12 результатов через 1 с, 37 через 3 с, все через
    7 с (по 4 по порядку — 18,5 с, все сразу — 1,5 с); всё, что держит Go, на пике 20,4 МиБ (по 4 — 18,8, все
    сразу — 28,3, после проверки 18–19). На телефоне по LTE и с мёртвыми серверами (таймаут 3 с держит слот) —
    порядка 10–15 с; до конца первой проверки leastLoad выбирает из уже проверенных. Сколько первых проверок ещё
    идёт — `burst.TitanChecking` (`titan` `memStats` → `checking`). Контекст его проб помечен
    (`titanProbeContext`): транспорты с пулами дают каждой свои соединение и рукопожатие (выше).
- `XrayRunConfig`: каждый DNS-запрос телефона — отдельный UDP-поток в TUN, и DNS-выход держал его
  `connIdle` (300 с). Выходы `dns-out` и `protocol: dns` получают свой уровень политики (9 или следующий,
  который в конфиге панели не занят) с `connIdle` 10 с. Нет access- и DNS-логов; нет `api`, `stats`,
  `metrics` и правил, ведущих на их теги (скорость приложение берёт со счётчиков utun). Балансировщики,
  observatory и остальные правила панели не меняются.
- Лимит Go (`titan` `setMemoryLimit`, `memory.go`, `goLimitFor`): лимит туннеля − max(footprint − память Go,
  4 МиБ) − 11 МиБ («fit»), но не ниже того, что нужно самому Go, и тогда самое большее на 2 МиБ выше порога
  сторожа (лимит − вне Go как есть, не меньше 1 МиБ, − 6 МиБ, «need»); сборка мусора заняла больше четверти ядра (за 5 с и больше между
  вызовами) — до этого же потолка на минуту («gc»); не меньше 24 МиБ («min»). Память Go — `total − released` (её и считает мягкий лимит);
  вне Go — footprint минус это: журнал на телефоне (24.10, Go до и после у 4 перезапусков) — 2,2–3,1 МиБ во всех 8
  замерах при Go 30,2–38,9 МиБ. По-настоящему не Go больше, ~6–7 МиБ (данные самой библиотеки, Swift,
  NetworkExtension, malloc), но в `total − released` Go есть ~3,8 МиБ отображённого и ни разу не тронутого
  (тривиальная программа на Go 1.27: 5,1 МиБ против 1,25 резидентных), а footprint по лимиту Go предсказывает
  именно эта разность. Раньше здесь было 12 МиБ (оценка 11–15, на телефоне не мерилась): лимит стоял на 8–9 МиБ
  ниже задуманного, 35 МиБ при footprint 38–41, и GC работал против него все минуты между перезапусками (Go
  перед каждым — 37,2–38,9, выше лимита). 11 МиБ — перелёт за мягкий лимит и старт перезапуска: Go у своего
  лимита оставляет footprint на 3 МиБ ниже порога сторожа (42 из 50; при пороге 44 было 9). Нужно Go — живая куча, всё, что он держит помимо
  объектов и свободных страниц (незанятое в спанах, стеки, метаданные), и место до следующей сборки (доля GOGC от живой кучи, не меньше 3 МиБ). Лимит ниже этого
  держал GC в работе без остановки и ничего не освобождал, а footprint стоял ниже порога сторожа — никто ничего
  не делал. Стенд (живая куча 20 МиБ, GOGC 10, `FreeOSMemory` раз в секунду, 6 потоков): при лимите 30 МиБ GC
  занимает 0,03 ядра, при 29 — 0,4, при 24–28 — почти целое ядро; «нужно» по формуле — 30–31. Теперь при 50 МБ:
  35 МиБ, пока вне Go не больше 4 и Go хватает, до 44 − вне Go (41–42 при 2,2–3,1 МиБ журнала), когда Go нужно
  больше. Потолок на 2 МиБ выше порога сторожа, а не на пороге: Go держит своё под мягким лимитом с запасом (1 МиБ
  или 3% лимита), и при лимите на пороге footprint стоял чуть ниже порога — GC работал без остановки, сторож ничего
  не видел (стенд при тогдашнем пороге 45 из 50, вне Go 12, живая куча 25,5 МиБ: лимит 33 — тогдашний порог для
  Go — 0,92 ядра, footprint 44,7 все 30 с, чуть ниже того порога; 34 — 0,06; 35 — 0,03, footprint 45,5–46,5).
  Потолок считается от того, что вне Go на самом деле, а не от 4 МиБ «fit»: от них при 2,2–3,1 МиБ вне Go
  footprint у потолка стоял ниже порога — то самое состояние, от которого потолок и нужен (стенд: Go 1.27, 4
  потока, 20 МиБ/с, GOGC 10, `FreeOSMemory` раз в секунду, живая куча — `/gc/heap/live`; при пороге 44: лимит
  42 = 50 − 4 − 4, живая куча 30,0 МиБ — GC 0,58 ядра, footprint не выше 43,55 / 43,85 при 2,2 / 2,5 вне Go, 44 —
  ни в одном замере; потолок 43,5 при 2,5 вне Go — при 30,0 МиБ GC 0,05 ядра и footprint 44,6 в каждом замере, GC
  занят с 31,2 МиБ, 0,45 ядра, 45,05). При пороге 42: лимит 40 = 50 − 4 − 6, живая куча 27,9 МиБ — 0,28 ядра,
  footprint не выше 41,33 / 41,63, 42 — ни в одном замере; потолок 41,5 при 2,5 вне Go — при 27,9 МиБ GC 0,05
  ядра, footprint 42,6 (не выше 42,9), выше порога в каждом замере, при 28,5 — 0,13 и 42,8; GC занят с 29,2 МиБ
  (0,35 ядра, 43,0; при 30,0 — 0,63 и 43,7). Тогда решает сторож (перезапуск, если поможет; если нет — GC
  работает у лимита, его доля видна в карточке); footprint у потолка — лимит − 8 + 2 МиБ без запаса пейсера,
  42,6–43,7, сколько бы ни было вне Go: пока перезапуск отложен, от убийства его отделяет один новый
  остановившийся поток QUIC (+7,5, ниже), и на пути только перезапуск сразу на 47. Не меньше 1 МиБ вне Go —
  против неверного замера, при котором потолок подошёл бы к самому лимиту. GOGC 10 libXray остаётся. Туннель задаёт лимит после
  каждого `runXray` (первый ставит 30 МиБ libXray), раз в 10 с и при давлении памяти.
- Сторож в туннеле (`PacketTunnelProvider`, раздел Memory): `phys_footprint` раз в 10 с, раз в 5 с
  выше 35 МиБ (было раз в секунду: «Батарея на iOS»), раз в 200 мс ближе 10 МиБ к лимиту (лимит = footprint + `os_proc_available_memory()`,
  если iOS его не даёт — 50 МиБ), и события давления памяти: на них `freeMemory` (не чаще раза в 10 с), лимит Go
  и замер, но не перезапуск. Среди них и собственное предупреждение iOS на 80% лимита (XNU вешает его на
  счётчик `phys_footprint`, `PHYS_FOOTPRINT_WARNING_LEVEL`, и шлёт при каждом подъёме выше 40 МиБ из 50), а
  источнику, который просил `.critical`, iOS отдаёт его как critical (`memorystatus_warn_process`): раньше
  critical в 10 МиБ от лимита считался превышением, и все перезапуски по памяти начинались на 40,0–41,1 МБ
  (журнал 24.10, обе сборки) — порог в 45 МиБ не действовал. За 8 МиБ до лимита (42 из 50), если
  перезапуск сейчас возможен и поможет, сначала `freeMemory` и новый замер через 0,3 с. Почему 8: новый поток
  QUIC (Hysteria, XHTTP/3), который встал (плеер на паузе), держит 6 МиБ данных, выданных рукопожатием, —
  +7,5 МиБ кучи (полный пакет в куче — 1,2 его данных), — пока стоит: quic-go отменяет остановившиеся, только
  когда они держат больше половины окна соединения (8 МиБ), один такой — никогда. От чуть ниже 42 он оставляет
  footprint ниже лимита (49,5), выше 42 приходит перезапуск. Здесь было 6 МиБ (44 из 50) «до убийства ещё
  6 МиБ, сколько поток получает до проверки через 2 с» — неверно: и куча 7,5, а не 6, и проверка до одного
  потока не доходит; с 43,9 тот же поток — 51,4, убийство, если перезапуск на 47 не успел (от 47 до 50 —
  2,4 МиБ данных, при 100 Мбит/с — 0,2 с, одна проверка раз в 200 мс). Модель ревью (Go 1.27, `goLimitFor`,
  сторож — его тики, `freeMemory` и 0,3 с, перезапуск на 47; поток 6 МиБ в буферах пакетов): при пороге 44 и
  footprint у порога 100 Мбит/с убивали в 1 из 4 прогонов, от 42,3 — 200 Мбит/с; при пороге 42 — 47,9–48,8
  при 100 Мбит/с, 48,7–49,9 при 200. Пока перезапуск отложен (рано, не поможет), footprint может стоять выше
  порога, Go у потолка (42,6–43,7, выше): тогда от того же потока спасает только перезапуск сразу на 47 (в
  модели 100 Мбит/с убивали и при пороге 42, 50 — нет: 47,6–47,8). Если после `freeMemory`
  обошлось — без перезапуска (счётчик). `freeMemory` сторожа перед перезапуском — не чаще раза в 10 с
  (полная сборка на очереди туннеля): раньше, пока перезапуск был отложен, он шёл каждые 0,4 с; выше 35 МиБ под
  порогом и пока перезапуск отложен — раз в 5 с (`freeBusy`: libXray теперь отдаёт память раз в минуту, не
  каждую секунду). Иначе — мягкий перезапуск: «Подключаемся…», Xray останавливается, пулы его транспортов закрываются,
  клиент протокола останавливается, Go отдаёт память, всё запускается снова с теми же повторами, что при
  смене сети. Перезапуск рвёт все соединения, поэтому он только если освободит хотя бы 3 МиБ сверх того, что
  осталось после прошлого запуска Xray; иначе в журнале «перезапуск по памяти не поможет: …» (раз до
  следующего перезапуска). Это «осталось» меряется, когда новый Xray закончил первую проверку серверов (до
  того открыты собственные соединения её проб, по 12 сразу, и каждое закрывается с пробой, у клиентов XHTTP
  проб — без keep-alive, который держал бы закрытые в куче 45 с; когда пробы клали соединения в пулы, замер
  через 5 с был на 1,5–3 МиБ ниже при 85 выходах, и бесполезные перезапуски казались полезными), не раньше 5
  и не позже 25 с после старта, наименьшее из трёх
  замеров раз в секунду (приложения переподключаются), годно 5 мин. Не чаще раза в 30 с, считая и перезапуски
  при смене сети. Перезапуск по памяти, после которого память меньше чем через 3 мин снова у порога, её не
  удержал: следующие идут вдвое реже (60, 120, 240 с), в журнале «перезапуск по памяти продержался N с:
  следующие не чаще раза в M с …»; память 3 мин ниже порога — снова 30 с. Удержал ли — по тому, когда память
  впервые после него снова у порога, а не по тому, когда пришёл следующий перезапуск: раньше пауза сама его
  откладывала, и в 180 с сбрасывалась в 30 с — перезапуски шли через 30, 60, 120, 180, 30, … с, а 240 не
  наступало. Ближе 3 МиБ к лимиту (47 из 50) — через 10 с после прошлого, без этой паузы и сразу, без `freeMemory` и замера
  через 0,3 с (если перезапуск поможет): перезапуск лучше убийства, `restart` сам отдаёт память Go, а libXray —
  каждую секунду. Пока перезапуск отложен, сторож решает заново на каждом замере, не повторяя `freeMemory`. Перезапуск при смене сети, который ждёт
  (до 20 с), сторож делает сразу вместо него. «Перезапуск по памяти: A → B» в журнале сначала с B сразу
  после старта, потом — «через N с» с B того замера и памятью Go до и после. Сам туннель сторож не завершает.
- Маркер: туннель пишет `running.json` в свой Caches при старте, раз в 9 с и на замере, где footprint

  на каждом старте проверял все выходы сразу; окна HTTP/2, gRPC и QUIC и буфер загрузки HTTP/2 копили

## Батарея на iOS

Телефон владельца (Аккумулятор, сутки, testflight/10 = eb3723e, АВТО: burst observatory и leastLoad на ~60
выходах): «Titan VPS — на экране 1 мин, в фоновом режиме 7 ч 54 мин — 27 %», больше только у Telegram (31 % за
2 ч 12 мин на экране). iOS относит к приложению CPU и радио его Network Extension. Что будило туннель и что
изменено (поверх ветки памяти ios-mem3; стенд и бенч — в конце раздела):

- Лимит Go ниже того, что Go держит (исправлено в ios-mem3, здесь проверено). В testflight/10 «вне Go» бралось
  не меньше 12 МиБ: лимит 30–35 МиБ при Go 37–39 (журнал 24.10), GC работал без остановки. Бенч, живая куча
  28,5 МиБ (footprint 38–40, как в журнале), 3 МиБ/с: по формуле testflight/10 лимит 35 («gc»), GC 0,90 ядра,
  3488 сборок в минуту, весь CPU 0,99 ядра; по формуле ios-mem3 — 38,5 («need»), 0,035 ядра, 122 в минуту,
  0,06. При 24 МиБ живой обе дают 35 и 0,03 ядра. Почти ядро всё время, пока Go выше 35, — вероятно, большая
  часть 27 %.
- `FreeOSMemory` libXray каждую секунду: полная сборка (вся живая куча) и возврат всех свободных страниц раз в
  секунду при любом трафике. Теперь раз в минуту (`xray-mem/apply_libxray.py`: `libxray_free.go` →
  `memory/titan_free.go`, тест `TestTitanFree` в сборке); выше 35 МиБ под порогом и пока перезапуск отложен
  свободные страницы раз в 5 с отдаёт сторож (`freeBusy`, на замерах, которые там и так идут), на давлении памяти
  и перед перезапуском — как было. Стенд без трафика: CPU 0,365 → 0,105 с в минуту, GC 0,223 → 0,030 с, сборок

## Диагностика на сервере

Захват трафика на ноде для одного клиента:

```
timeout 90 tcpdump -Z root -ni any -w /root/t.pcap 'port <порт>'
tcpdump -nr /root/t.pcap -vv 'src host <IP клиента> and tcp[tcpflags] & tcp-syn != 0' | paste - - | head
tcpdump -nr /root/t.pcap -q 'host <IP клиента>' | head -100
```

Внешний IP устройства виден в техническом режиме, раздел «Сеть».
