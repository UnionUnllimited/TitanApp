# Покупки App Store: что нужно на стороне бота и панели

Спецификация для бэкенда (бот / панель). Приложение iOS продаёт подписку через App Store
(StoreKit 2) и передаёт каждую покупку боту, а бот продлевает подписку того ключа, с которым
куплено. В этом файле нет и не должно быть секретов: ключи App Store Connect, адреса и токены
панели хранятся только на сервере.

## Что делает приложение

- Тарифы App Store — автопродлеваемые подписки одной группы. Идентификаторы продуктов (пока
  заглушки, их нужно завести в App Store Connect с теми же id) — `ProductIDs` в
  `ios/TitanVPS/Purchases.swift`:

  | productId | Период |
  |---|---|
  | `com.titanvps.ios.sub.month` | 1 месяц |
  | `com.titanvps.ios.sub.quarter` | 3 месяца |
  | `com.titanvps.ios.sub.year` | 1 год |

- Покупка идёт с `appAccountToken` (см. ниже), поэтому любая транзакция этой подписки, в том
  числе продления, которые App Store делает без приложения, несёт метку ключа.
- После покупки приложение отправляет транзакцию на адрес `Config.purchaseEndpoint`
  (`ios/TitanVPS/Subscription.swift`; пока `nil`) и **завершает транзакцию
  (`Transaction.finish()`) только на ответ 2xx**. Пока транзакция не завершена, StoreKit
  отдаёт её приложению снова: при каждом запуске (`Transaction.updates`) и по кнопке
  «Восстановить покупки». Пользователь до этого видит «Покупка получена — подписка продлится
  после проверки».
- Приложение отправляет только покупки, у которых `appAccountToken` совпадает с ключом, под
  которым оно сейчас вошло, или которых нет (покупка без метки — например, по коду предложения
  из App Store). Покупку, сделанную с другим ключом, оно оставляет незавершённой.
- После 2xx приложение перечитывает подписку (новая дата окончания должна прийти в
  `subscription-userinfo`, как сейчас).

Чтобы не добавлять в публичный код новый домен, endpoint удобно принимать на тех же хостах, что
и подписка (`Config.hosts`); тогда в приложении достаточно пути.

## Метка ключа: keyToken, appAccountToken, хеш

Все три считаются из одной строки — `keyToken`:

- `keyToken` — последний UUID в ссылке подписки (как его ищет `AccountAPI`, в нижнем регистре);
  если UUID нет — путь ссылки без `/` по краям. Хост не участвует: ссылка на любом из хостов
  даёт одно и то же.
- `digest = SHA-256(keyToken в UTF-8)`.
- `appAccountToken` — первые 16 байт `digest` как UUID версии 8:
  `b[6] = (b[6] & 0x0F) | 0x80`, `b[8] = (b[8] & 0x3F) | 0x80`, запись в нижнем регистре.
- Хеш ключа (для запроса в поддержку) — первые 12 hex-символов `digest`.

Бот может посчитать `appAccountToken` и хеш для каждого пользователя один раз и хранить их в
индексе: так уведомление App Store находит пользователя без участия приложения.

Пример на Python:

```python
import hashlib, uuid
d = hashlib.sha256(key_token.encode()).digest()
b = bytearray(d[:16]); b[6] = (b[6] & 0x0F) | 0x80; b[8] = (b[8] & 0x3F) | 0x80
app_account_token = str(uuid.UUID(bytes=bytes(b)))
key_hash = d.hex()[:12]
```

## Endpoint доставки покупки

`POST https://…/…` (только HTTPS), `Content-Type: application/json`,
`User-Agent: Titan(IOS/<версия>)`.

```json
{
  "signedTransaction": "<JWS транзакции от App Store>",
  "key": "<ссылка подписки, с которой куплено>",
  "appAccountToken": "<UUID, см. выше>",
  "clientId": "<«Ваш ID» из кабинета, если приложение его знает>",
  "transactionId": "…",
  "originalTransactionId": "…",
  "productId": "com.titanvps.ios.sub.month"
}
```

`transactionId`, `originalTransactionId` и `productId` — только подсказки для журнала. Верить
можно лишь тому, что внутри проверенного `signedTransaction`.

### Проверка

1. Проверить JWS. Проще всего — официальной библиотекой Apple App Store Server Library
   (Python, Node.js, Java, Swift), `SignedDataVerifier`: корневые сертификаты Apple
   (Apple Root CA – G3), `bundleId` = `com.titanvps.ios`, `appAppleId` (для Production),
   окружение. Вручную: цепочка `x5c` из заголовка до Apple Root CA – G3 (листовой сертификат с
   OID `1.2.840.113635.100.6.11.1`, промежуточный с `1.2.840.113635.100.6.2.1`), подпись ES256.
   Дополнительно (или вместо этого) можно запросить транзакцию у App Store Server API:
   `GET /inApps/v1/transactions/{transactionId}` с JWT, подписанным In-App Purchase key из App
   Store Connect (ключ `.p8` — только на сервере).
2. Проверить поля: `bundleId`, `type` = `Auto-Renewable Subscription`, `productId` из таблицы
   выше, нет `revocationDate`. `environment` = `Sandbox` тоже принимать и продлевать: App Review
   и TestFlight покупают именно в Sandbox, и если покупка ревьюера ничего не продлит, сборку
   отклонят. Отличать их по `environment` (пометка в журнале, отдельный учёт).
3. Найти пользователя по `key` (как бот находит подписку по ссылке). Если в транзакции есть
   `appAccountToken`, он должен совпасть с посчитанным для этого ключа (сравнивать без учёта
   регистра).

### Продление и идемпотентность

- `originalTransactionId` — это сама подписка App Store, одна на все её продления. Первая
  доставка привязывает `originalTransactionId → пользователь`. Повторная доставка той же
  подписки с другим ключом — `409` (приложение оставит транзакцию, разберётся поддержка).
- `transactionId` — каждый оплаченный период (покупка и каждое продление). Каждый
  `transactionId` продлевает подписку ровно один раз; повтор — сразу `200`, ничего не меняя.
  Поэтому «идемпотентность по originalTransactionId» на деле — привязка по
  `originalTransactionId` и учёт по `transactionId`.
- `productId → тариф`: дни (`month` — 1 месяц, `quarter` — 3 месяца, `year` — 12 месяцев)
  добавляются к текущей подписке, как у тарифов кабинета («Дни добавятся к текущей подписке»).
  Лимит устройств и трафик на обходах — как у соответствующего тарифа бота; уже выбранный
  пользователем лимит устройств не меняется. Другой вариант — ставить окончание не раньше
  `expiresDate` транзакции; выбрать один и держаться его.

### Ответ

- `200` — продлено или уже было продлено этой транзакцией. Тело любое (например,
  `{"ok": true, "expire": 1767225600}`), приложение его не читает и завершает транзакцию.
- `400` — не тот формат; `401`/`422` — JWS не прошёл проверку; `404` — ключ не найден;
  `409` — подписка App Store уже привязана к другому пользователю; `5xx` — временная ошибка.
  На всё, кроме 2xx, приложение транзакцию не завершает и пришлёт её снова.

## App Store Server Notifications V2

В App Store Connect → приложение → App Information → App Store Server Notifications указать
URL (Production и Sandbox, версия 2). Так бот узнаёт о продлениях, возвратах и окончании, даже
если приложение не открывали.

- Тело — `{"signedPayload": "<JWS>"}`. Проверить так же, как транзакцию (та же библиотека),
  внутри — `notificationType`, `subtype`, `notificationUUID`, `data.signedTransactionInfo`,
  `data.signedRenewalInfo`.
- Пользователя искать по `appAccountToken` транзакции (индекс выше), иначе по привязке
  `originalTransactionId`.
- Что делать:

  | notificationType (subtype) | Действие |
  |---|---|
  | `SUBSCRIBED` (`INITIAL_BUY`, `RESUBSCRIBE`), `DID_RENEW`, `OFFER_REDEEMED` | продлить по `transactionId` (как в endpoint) |
  | `DID_FAIL_TO_RENEW` (`GRACE_PERIOD`) | доступ до `gracePeriodExpiresDate` из renewal info |
  | `EXPIRED`, `GRACE_PERIOD_EXPIRED` | ничего не продлевать; подписка закончится по своей дате |
  | `REFUND`, `REVOKE` | снять дни, добавленные этой транзакцией (`transactionId`) |
  | `REFUND_REVERSED` | вернуть их |
  | `DID_CHANGE_RENEWAL_STATUS`, `DID_CHANGE_RENEWAL_PREF` | только записать (смена тарифа — со следующего продления) |
  | `CONSUMPTION_REQUEST` | при желании ответить через App Store Server API |
  | `TEST` | ответить 200 |

- Отвечать `200` быстро; на другие ответы App Store повторяет. Повторы отбрасывать по
  `notificationUUID`; продление всё равно учитывается по `transactionId`, так что уведомление и
  доставка из приложения не продлят дважды.

## Удаление аккаунта

Профиль → Аккаунт → «Удалить аккаунт» в приложении: приложение удаляет с устройства ключ,
избранное, напоминания и VPN-профиль, копирует текст и открывает поддержку (`support-url` из
заголовков подписки, иначе бот):

```
Прошу удалить мой аккаунт Titan VPS. ID: <ID>
```

`<ID>` — первое, что приложение знает:

1. «Ваш ID» из личного кабинета (`#client-id-label`), если пользователь открывал кабинет с
   этим ключом;
2. `username` из `GET /api/sub/{uuid}/info`, если бот его там отдаёт (поле верхнего уровня);
3. `<12 hex> (хеш ключа)` — хеш из раздела выше.

Что делает поддержка: находит пользователя, удаляет пользователя панели (ключ перестаёт
работать), его устройства и данные в боте, отвечает пользователю. Подписку App Store бот
отменить не может: пользователь отменяет её сам (Настройки iOS → Apple ID → Подписки), возврат —
через Apple (reportaproblem.apple.com). Привязку `originalTransactionId` можно удалить вместе с
пользователем; если App Store потом пришлёт продление этой подписки, его не к кому применить —
ответить 200 и ничего не делать.

App Review просит, чтобы удаление начиналось в приложении и не требовало звонка или письма.
Следующий шаг, чтобы обойтись без поддержки: endpoint удаления (`POST`, тело — ключ, ответ 200
после удаления), который приложение вызовет само; тогда копирование текста останется
запасным путём.
