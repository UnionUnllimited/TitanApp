# Покупки App Store: что нужно на стороне бота и панели

Спецификация для бэкенда (бот / панель). Приложение iOS продаёт подписку и гигабайты для
обходов через App Store (StoreKit 2) и передаёт каждую покупку боту, а бот продлевает подписку
того ключа, с которым куплено, или, если ключа ещё нет, создаёт подписку и возвращает её ключ.
В этом файле нет и не должно быть секретов: ключи App Store Connect, адреса и токены панели
хранятся только на сервере.

Без этого endpoint покупка ревьюера App Review ничего не продлит и не выдаст ключ, а сборку с
такими покупками, скорее всего, отклонят: его нужно сделать до отправки на ревью. До тех пор в
заметках для App Review (App Store Connect → App Review Information → Notes) нужен рабочий
демо-ключ.

## Что делает приложение

- Продукты App Store (пока заглушки, их нужно завести в App Store Connect с теми же id) —
  `ProductIDs` в `ios/TitanVPS/Purchases.swift`:

  | productId | Тип | Что даёт |
  |---|---|---|
  | `com.titanvps.ios.sub.month` | автопродлеваемая подписка | 1 месяц |
  | `com.titanvps.ios.sub.quarter` | автопродлеваемая подписка | 3 месяца |
  | `com.titanvps.ios.sub.year` | автопродлеваемая подписка | 1 год |
  | `com.titanvps.ios.gb.small` | расходуемая (consumable) | пакет ГБ для обходов, как меньший пакет бота |
  | `com.titanvps.ios.gb.medium` | расходуемая | средний пакет |
  | `com.titanvps.ios.gb.large` | расходуемая | больший пакет |

  Подписки — одна группа подписок. Описание каждого продукта в App Store Connect (что входит:
  лимит устройств, гигабайты на обходах) приложение показывает под ним в «Тарифах». Пакеты ГБ
  показываются только по кнопкам «Добавить ГБ» и только с ключом; пока App Store их не отдаёт,
  их карточки в «Тарифах» нет. Завести их нужно до ревью: гигабайты, которые продаёт бот и
  расходует приложение, App Review требует продавать и через App Store (3.1.3(b)). Размеры
  пакетов — как у пакетов «Гигабайты для обходов» в кабинете; id можно переименовать (вместе с
  `ProductIDs`).
- Оплата мимо App Store: «Другие методы» в «Тарифах» (кабинет сайта во внешнем браузере) и
  вкладка «Тарифы» встроенного «Личного кабинета» (тарифы и коды сайта, страница оплаты внутри
  приложения) — по решению владельца во всех витринах
  (`AppStorePurchases.otherMethodsEverywhere`). App Review разрешает такие кнопки и ссылки
  только в витрине США (3.1.1(a)); `false` оставит их только там. Бот как место, где взять
  ключ, приложение показывает только в витрине США при любом значении. Для бэкенда это ничего
  не меняет: такие оплаты идут через сайт, как сейчас.
- Коды предложений App Store (Offer Codes в App Store Connect): «Ввести код предложения» в
  «Тарифах», когда ключ уже введён. Транзакция по коду приходит без `appAccountToken` и
  доставляется с ключом, как покупка (уведомление `OFFER_REDEEMED` ниже). Коды сайта — во
  вкладке «Тарифы» кабинета, как раньше.

- Покупка идёт с `appAccountToken` (см. ниже), поэтому любая транзакция этой подписки, в том
  числе продления, которые App Store делает без приложения, несёт метку ключа. Покупка до ввода
  ключа (экран ввода ключа → «Подписка через App Store») идёт со случайным `appAccountToken`
  этого устройства (один на устройство, приложение хранит его до «Удалить аккаунт»).
- После покупки приложение отправляет транзакцию на адрес `Config.purchaseEndpoint`
  (`ios/TitanVPS/Subscription.swift`; пока `nil`) и **завершает транзакцию
  (`Transaction.finish()`) только на ответ 2xx**. Пока транзакция не завершена, StoreKit
  отдаёт её приложению снова: при каждом запуске (`Transaction.updates`) и по кнопке
  «Восстановить покупки». Пользователь до этого видит «Покупка получена — подписка продлится
  после проверки».
- Приложение с ключом отправляет только покупки, у которых `appAccountToken` совпадает с этим
  ключом или с токеном этого устройства, или которых нет (покупка без метки — например, по коду
  предложения из App Store). Покупку, сделанную с другим ключом, оно оставляет незавершённой.
- Приложение без ключа отправляет покупку **без `key`**: сразу после покупки или по кнопке
  «Восстановить покупки» на экране ввода ключа (так подписка, купленная на другом iPhone или
  iPad с тем же Apple ID, возвращает свой ключ). Сам по себе, без нажатия, — только первую
  транзакцию покупки с токеном этого устройства, не продления: после «Выйти» приложение не
  входит обратно само. Только подписки: пакетам ГБ нужен ключ.
- После 2xx приложение перечитывает подписку (новая дата окончания должна прийти в
  `subscription-userinfo`, как сейчас); без ключа — входит с ключом из ответа.

Чтобы не добавлять в публичный код новый домен, endpoint удобно принимать на тех же хостах, что
и подписка (`Config.hosts`); тогда в приложении достаточно пути.

## Метка ключа: keyToken, appAccountToken, хеш

Все три считаются из одной строки — `keyToken`:

- `keyToken` — последний UUID в ссылке подписки (как его ищет `AccountAPI`, в нижнем регистре);
  если UUID нет — путь ссылки без `/` по краям. Хост не участвует: ссылка на любом из хостов
  даёт одно и то же.
- `digest = SHA-256(keyToken в UTF-8)`.
- `appAccountToken` — первые 16 байт `digest` как UUID версии 8:
  `b[6] = (b[6] & 0x0F) | 0x80`, `b[8] = (b[8] & 0x3F) | 0x80`, запись в нижнем регистре.
- Хеш ключа (для запроса в поддержку) — первые 12 hex-символов `digest`.

Бот может посчитать `appAccountToken` и хеш для каждого пользователя один раз и хранить их в
индексе: так уведомление App Store находит пользователя без участия приложения.

Пример на Python:

```python
import hashlib, uuid
d = hashlib.sha256(key_token.encode()).digest()
b = bytearray(d[:16]); b[6] = (b[6] & 0x0F) | 0x80; b[8] = (b[8] & 0x3F) | 0x80
app_account_token = str(uuid.UUID(bytes=bytes(b)))
key_hash = d.hex()[:12]
```

## Endpoint доставки покупки

`POST https://…/…` (только HTTPS), `Content-Type: application/json`,
`User-Agent: Titan(IOS/<версия>)`.

```json
{
  "signedTransaction": "<JWS транзакции от App Store>",
  "key": "<ссылка подписки, с которой куплено>",
  "appAccountToken": "<UUID, см. выше>",
  "clientId": "<«Ваш ID» из кабинета, если приложение его знает>",
  "transactionId": "…",
  "originalTransactionId": "…",
  "productId": "com.titanvps.ios.sub.month"
}
```

`key`, `appAccountToken` и `clientId` есть, только когда приложение уже вошло с ключом.
`transactionId`, `originalTransactionId` и `productId` — только подсказки для журнала. Верить
можно лишь тому, что внутри проверенного `signedTransaction`.

### Проверка

1. Проверить JWS. Проще всего — официальной библиотекой Apple App Store Server Library
   (Python, Node.js, Java, Swift), `SignedDataVerifier`: корневые сертификаты Apple
   (Apple Root CA – G3), `bundleId` = `com.titanvps.ios`, `appAppleId` (для Production),
   окружение. Вручную: цепочка `x5c` из заголовка до Apple Root CA – G3 (листовой сертификат с
   OID `1.2.840.113635.100.6.11.1`, промежуточный с `1.2.840.113635.100.6.2.1`), подпись ES256.
   Дополнительно (или вместо этого) можно запросить транзакцию у App Store Server API:
   `GET /inApps/v1/transactions/{transactionId}` с JWT, подписанным In-App Purchase key из App
   Store Connect (ключ `.p8` — только на сервере).
2. Проверить поля: `bundleId`, `productId` из таблицы выше и его `type`
   (`Auto-Renewable Subscription` для подписок, `Consumable` для пакетов ГБ), нет
   `revocationDate`. `environment` = `Sandbox` тоже принимать и продлевать: App Review
   и TestFlight покупают именно в Sandbox, и если покупка ревьюера ничего не продлит, сборку
   отклонят. Отличать их по `environment` (пометка в журнале, отдельный учёт).
3. С `key`: найти пользователя по ключу (как бот находит подписку по ссылке). Если в транзакции
   есть `appAccountToken`, он должен совпасть с посчитанным для этого ключа или с токеном,
   уже привязанным к этому пользователю; токен, не привязанный ни к кому (покупка до ввода
   ключа), привязать к нему. Токен другого пользователя — `409`. Сравнивать без учёта регистра.
4. Без `key` (только подписки): пользователь по привязке `originalTransactionId`; если её нет
   (первая доставка покупки, сделанной до ввода ключа) — создать пользователя с тарифом этого
   `productId`, привязать к нему `originalTransactionId` и `appAccountToken` транзакции. Пакет
   ГБ без `key` — `422`. Кто прислал проверенный JWS подписки, тот её владелец: подделать его
   нельзя, а получить может только приложение на устройстве с этим Apple ID.

### Продление и идемпотентность

- `originalTransactionId` — это сама подписка App Store, одна на все её продления. Первая
  доставка привязывает `originalTransactionId → пользователь`. Повторная доставка той же
  подписки с другим ключом — `409` (приложение оставит транзакцию, разберётся поддержка).
- `transactionId` — каждый оплаченный период (покупка и каждое продление). Каждый
  `transactionId` продлевает подписку ровно один раз; повтор — сразу `200`, ничего не меняя.
  Поэтому «идемпотентность по originalTransactionId» на деле — привязка по
  `originalTransactionId` и учёт по `transactionId`.
- `productId → тариф`: дни (`month` — 1 месяц, `quarter` — 3 месяца, `year` — 12 месяцев)
  добавляются к текущей подписке, как у тарифов кабинета («Дни добавятся к текущей подписке»).
  Лимит устройств и трафик на обходах — как у соответствующего тарифа бота; уже выбранный
  пользователем лимит устройств не меняется. Другой вариант — ставить окончание не раньше
  `expiresDate` транзакции; выбрать один и держаться его. Описание продукта в App Store Connect
  должно говорить то же самое (приложение показывает его в «Тарифах»).
- Пакет ГБ: гигабайты пакета добавляются к трафику на обходах, тоже ровно один раз на
  `transactionId`. Пакет не продлевается и привязки `originalTransactionId` не требует.

### Ответ

- `200` — продлено или уже было продлено этой транзакцией. С `key` тело любое (например,
  `{"ok": true, "expire": 1767225600}`), приложение его не читает и завершает транзакцию.
  Без `key` тело обязательно — ключ (ссылка подписки на одном из хостов `Config.hosts`) того
  пользователя, к которому привязана подписка, и на каждую повторную доставку тот же:

  ```json
  {"ok": true, "key": "https://…/…"}
  ```

  Приложение входит с этим ключом и только потом завершает транзакцию; нет `key` в ответе —
  транзакция остаётся и придёт снова.
- `400` — не тот формат; `401`/`422` — JWS не прошёл проверку; `404` — ключ не найден;
  `409` — подписка App Store уже привязана к другому пользователю; `5xx` — временная ошибка.
  На всё, кроме 2xx, приложение транзакцию не завершает и пришлёт её снова.

## App Store Server Notifications V2

В App Store Connect → приложение → App Information → App Store Server Notifications указать
URL (Production и Sandbox, версия 2). Так бот узнаёт о продлениях, возвратах и окончании, даже
если приложение не открывали.

- Тело — `{"signedPayload": "<JWS>"}`. Проверить так же, как транзакцию (та же библиотека),
  внутри — `notificationType`, `subtype`, `notificationUUID`, `data.signedTransactionInfo`,
  `data.signedRenewalInfo`.
- Пользователя искать по `appAccountToken` транзакции (индекс выше), иначе по привязке
  `originalTransactionId`.
- Что делать:

  | notificationType (subtype) | Действие |
  |---|---|
  | `SUBSCRIBED` (`INITIAL_BUY`, `RESUBSCRIBE`), `DID_RENEW`, `OFFER_REDEEMED` | продлить по `transactionId` (как в endpoint) |
  | `DID_FAIL_TO_RENEW` (`GRACE_PERIOD`) | доступ до `gracePeriodExpiresDate` из renewal info |
  | `EXPIRED`, `GRACE_PERIOD_EXPIRED` | ничего не продлевать; подписка закончится по своей дате |
  | `REFUND`, `REVOKE` | снять дни (или ГБ пакета), добавленные этой транзакцией (`transactionId`) |
  | `REFUND_REVERSED` | вернуть их |
  | `DID_CHANGE_RENEWAL_STATUS`, `DID_CHANGE_RENEWAL_PREF` | только записать (смена тарифа — со следующего продления) |
  | `CONSUMPTION_REQUEST` | при желании ответить через App Store Server API |
  | `TEST` | ответить 200 |

- Отвечать `200` быстро; на другие ответы App Store повторяет. Повторы отбрасывать по
  `notificationUUID`; продление всё равно учитывается по `transactionId`, так что уведомление и
  доставка из приложения не продлят дважды.

## Удаление аккаунта

Профиль → Аккаунт → «Удалить аккаунт» в приложении. Если у Apple ID есть действующая подписка
App Store этого приложения, приложение сначала говорит, что Apple продолжит её списывать, и
предлагает «Управление подпиской» (отменить); отмену бот за пользователя сделать не может.

### Endpoint удаления (основной путь)

`Config.deletionEndpoint` в `ios/TitanVPS/Subscription.swift` (пока `nil`). Удобно на тех же
хостах, что и подписка (`Config.hosts`), как и endpoint покупок.

`POST https://…/…`, `Content-Type: application/json`, `User-Agent: Titan(IOS/<версия>)`:

```json
{
  "key": "<ссылка подписки>",
  "appAccountToken": "<UUID ключа, см. выше>",
  "clientId": "<«Ваш ID» из кабинета, если приложение его знает>"
}
```

- Найти пользователя по `key`, удалить пользователя панели (ключ перестаёт работать), его
  устройства и данные в боте, привязки `originalTransactionId` и `appAccountToken`. Записи о
  покупках, которые нужно хранить для учёта, отвязать от пользователя.
- Ответить `200`, когда удалено (или если такого пользователя уже нет — повтор). Приложение
  удаляет ключ и данные с устройства и пишет «Аккаунт удалён». На любой другой ответ или без
  ответа приложение переходит к запасному пути ниже.
- Если App Store потом пришлёт продление подписки удалённого пользователя, его не к кому
  применить — ответить 200 и ничего не делать.

### Запасной путь: запрос в поддержку

Пока endpoint нет (или он не ответил), приложение удаляет с устройства ключ, избранное,
напоминания и VPN-профиль, копирует текст и открывает поддержку (`support-url` из заголовков
подписки, иначе бот):

```
Прошу удалить мой аккаунт Titan VPS. ID: <ID>
```

`<ID>` — первое, что приложение знает:

1. «Ваш ID» из личного кабинета (`#client-id-label`), если пользователь открывал кабинет с
   этим ключом;
2. `username` из `GET /api/sub/{uuid}/info`, если бот его там отдаёт (поле верхнего уровня);
3. `<12 hex> (хеш ключа)` — хеш из раздела выше.

Приложение обещает пользователю: аккаунт и подписку в боте удалят **в течение 7 дней**, и
поддержка ответит в чате, когда всё удалено. Что делает поддержка: находит пользователя,
удаляет то же, что endpoint выше, и пишет пользователю подтверждение. Возврат за подписку App
Store — только через Apple (reportaproblem.apple.com).

App Review просит, чтобы удаление начиналось в приложении и не требовало звонка, письма или
чата поддержки, поэтому endpoint удаления нужен до отправки на ревью; копирование текста
остаётся запасным путём.
